# ADR-002 · 链上↔链下经济闭环

- **状态**：Proposed（待主理人 + 策划交叉评审）
- **日期**：2026-08-02
- **决策人**：程基岩（engineering-lead）
- **相关**：`onchain-offchain-economy-loop.md`、ADR-001

---

## 1. 上下文

ADR-001 划定了资产边界，但没回答**价值如何跨层流动**。需要解决：

- 链下高频资源（`strategic` 日产 20000、体力 120/日、琥珀币）如何映射到链上 `$TIDE`？
- `resources.json` 冻结了 `$TIDE` 的 `net_issuance ≤ 0`。这条红线如何**强制**而非"自觉遵守"？
- `SOFT_TO_HARD_RATE = 150`、`SOFT_EXCHANGE_DAILY_CAP = 3` 已冻结，但琥珀币在链下——
  **链上无法验证玩家真的持有 450 琥珀币**。这是本 ADR 的核心难题。
- 护岛日产要上链结算，但 `islands.json` **当前没有日产字段**（数据缺口）。
- D5 验收要求「跑 30 步资源通胀 ≤5%/天，`$TIDE` 净发行 ≤0」，链上化后需要新的验证方式。

---

## 2. 备选方案

### 关于总体结构

**方案 A · 自由双向兑换**：链上链下资源可自由互换。
- ❌ 双向套利 → 双通胀，SSOT 已明确「反向永久关闭」，直接否决。

**方案 B · 完全隔离**：链上经济与链下经济互不相通。
- ✅ 最安全，审计面为零
- ❌ 链上资产与游戏玩法脱节，链只是个"NFT 展柜"，玩法闭环断裂

**方案 C · 三闸门单向受控通道（采用）**：链下→链上的价值流动收敛到 3 个函数（占岛确权 / 软→硬兑换 / 日产领取），全部单向。
- ✅ 审计面收敛到 3 个函数
- ✅ 与 SSOT 冻结的单向兑换、日限口径完全一致
- ✅ 保留玩法闭环：打岛 → 产出 → 上链 → gacha → 更强的卡 → 打更强的岛

### 关于「链上无法验证琥珀币余额」（闸门 B）

| 方案 | 做法 | 取舍 |
|---|---|---|
| **B1 · 服务端签名授权** | 链下服务端核验余额后出具签名，链上验签 | ✅ 精确<br>❌ 引入中心化可信第三方，与 zk 去信任叙事**正面冲突**；服务端被攻破 = 无限增发 |
| **B2 · 琥珀币上链** | 让琥珀币成为链上 token | ❌ 违反 SSOT「不链上流通」冻结口径<br>❌ 软货币高频，fee 不可承受 |
| **B3 · 日限即上限（采用）** | 链上**只强制日限 3**，不验证余额；琥珀扣减在链下 | ✅ 零信任引入<br>✅ 损失有硬上界<br>❌ 玩家可绕过客户端白嫖 3 $TIDE/日 |
| B4 · zk 证明琥珀余额 | 链下余额做 Merkle 承诺，玩家证明余额 ≥450 | ✅ 精确且去信任<br>❌ 余额承诺根谁来维护？仍需可信方 → 回到 B1 |

**关键推理**：B3 的"漏洞"其实是可接受的，因为 **`SOFT_EXCHANGE_DAILY_CAP = 3` 本身就是设计发放量**。
即使 100% 玩家绕过客户端，全服增发量 = 玩家数 × 3/日，恰好等于设计上限，
`net_issuance ≤ 0` 的总护栏依然成立。**用经济护栏兜住技术上无法验证的部分**，比引入中心化服务端更符合项目定位。

## 3. 决定

### 3.1 采用三闸门单向结构（方案 C）

| 闸门 | 函数 | 方向 |
|---|---|---|
| A · 占岛确权 | `claim_island()` | 链下战斗结果 → 链上归属 |
| B · 软→硬兑换 | `exchange_soft_to_tide()` | 链下琥珀 → 链上 $TIDE（单向） |
| C · 日产领取 | `claim_island_yield()` | 链上归属 → 链上 $TIDE mint |

**除这 3 个函数外，不存在任何跨层价值流动。** 这是可审计性的基础。

### 3.2 闸门 B 采用 B3（日限即上限）

不验证琥珀余额，只在链上强制 `SOFT_EXCHANGE_DAILY_CAP = 3`。

### 3.3 `net_issuance ≤ 0` 用链上断言强制

```leo
assert(supply.minted <= supply.burned + supply.genesis);
```

置于**所有 mint 路径末尾**（闸门 B 与 C）。全服 burn 不足时 mint 交易 revert。

### 3.4 日产结算粒度：每日 1 次 claim（⚠ 依赖 A-06）

链上按 `(tier, 经过区块数)` 重算，链下累积数字仅作 UI 预览。
用 `last_claim_height` mapping 防重复领取。

## 4. 后果

### 正面

- 经济审计面收敛到 3 个函数 + 1 条供应量断言，极易 review，也极易向评委讲清楚。
- `net_issuance ≤ 0` 从"数值表里的一句话"变成"链上强制的不变量"——
  **把经济纪律写进代码**，是本项目相对普通链游的实质差异点。
- 闸门 B3 保持了零信任，没有为了可验证性引入中心化服务端。
- 与 SSOT 已冻结的经济口径（150 兑率、日限 3、单向、净发行≤0）**逐条对齐**，无需策划返工。

### 负面 / 需承担

- **通缩枯竭风险**：全服 burn（gacha + market_fee）不足时，玩家**领不到日产**（交易 revert）。
  - 缓解：设 `genesis_supply` 为赛季预算池，按 **`SEASON_DAYS = 90`** 外推设定（**不能用 30 步压测结论直接套**）；赛季结算（D85–90）时重置。
  - **需策划确认**：把"潮汐退去、海域贫瘠"做成可感知的世界状态是否可接受？这可以是特性，也可以是灾难，取决于表达。
- **闸门 B 可被白嫖 3 $TIDE/日**：已知且有界，接受。
- **日产领取不是实时的**：玩家需主动 claim，有"离线累积、上线领取"的体验模式（A-06）。
- **区块高度 ≠ 自然日 0 点（A-09）**：日限刷新时间会与游戏内 0 点存在偏移，UI 需明示"链上日"概念。

### 阻塞项

- ⚠ **闸门 C 当前无法实现**：`islands.json` 没有日产字段，`yield_by_tier` 无数据来源。
  **这是本 ADR 的头号阻塞，需策划优先补齐**（详见 `asset-ownership-boundary.md` §4.1）。

## 5. 验证方式

D5 验收扩展为**双账本对账**：

1. 链下经济模拟器逐日输出预测 claim 总量
2. 链上 `supply` mapping 记录实际 mint 总量
3. 断言两者逐日一致（偏差即为规则实现不一致）
4. 断言全服 mint ≤ 玩家数 × 3/日 + 日产理论上限
5. 断言 `minted ≤ burned + genesis` 全程成立

> 按 90 天跑，或用 30 步压缩模型跑后**显式外推到 90 天**再判定。

## 6. 复核触发条件

- 对齐假设 A-06 / A-07 / A-08 / A-09 中任一被推翻
- `islands.json` 日产字段补齐后，发现日产依赖驻防编队/建筑/皮肤加成（A-07 被推翻 → 闸门 C 需重新设计）
- 知识缺口 G-04（Aleo fee 与出块间隔实测）结果显示每日 claim 的 fee 不可承受
- 经济模拟显示 90 天内 `genesis_supply` 会枯竭
