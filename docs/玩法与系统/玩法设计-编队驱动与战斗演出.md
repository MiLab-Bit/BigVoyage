# 玩法设计 · 编队驱动与战斗演出（纯 Auto 模型 · 决策 A）

> 前置决策：用户选定 **A — 纯 Auto（无战斗操作）**。编队=唯一策略表达，战斗=纯函数演出层。
> 本文只设计「怎么玩」，不碰数值。数值基线见 `数据层/cards.json`（v0.2）与 `constants.md`。

---

## §0 一句话定位
**这是一款「布阵类策略游戏」**：玩家在开战前完成 100% 的策略表达，战斗是一场**可被解读、可回放、可学习**的确定性演出。乐趣 = 读敌情 → 组克制 → 预测 → 看演出验证 → 优化。

同类参照：自走棋的「布阵+观战」、战棋的「预设指令」、肉鸽的「冲分优化」。

---

## §1 核心循环重定义（编队驱动，非战斗驱动）

```
侦察敌情 → 解读(体系/威胁卡) → 编队(选卡+位序+预设目标) 
   → 预测(克制%/combo预览) → 开战(auto演出) → 复盘(日志高亮) → 调整 → 再战
```

- **有趣的那一下在「编队」**，不在战斗。战斗是「你的读盘对不对」的揭晓。
- 因此游戏的两大支柱变为：**① 编队空间的策略厚度** + **② 演出的可读性与爽感**。
- 这彻底解释了为何原文档「战斗模块空白」会致命：不是缺公式，是缺「玩家在编队时脑子里在算什么」。

---

## §2 编队作为「唯一策略表达」如何有厚度（不能只是选高数值）

厚度来自 5 个正交维度，让「同 COST 选哪张」永远是真实权衡：

| 维度 | 设计 | 制造的策略 |
|---|---|---|
| **位序** | 前排(扛)/中排(输出)/后排(控) — 决定谁先挨打、combo 链顺序 | 脆皮核心 vs 铁壁墙的摆放博弈 |
| **体系构成** | 纯一体系(mono, 软上限≤4) vs 混编 | mono 吃环境加成但怕互克；混编有 combo 但稀释体系技 |
| **预设目标** | 开战前设「优先击杀 X 卡 / 集火后排 / 保命拖回合」(属编队指令，非实时操作) | 速杀核心 vs 苟住打持久 |
| **COST 硬约束** | 10 点 / 5 槽，R1·SR2·SSR3·UR4 | 满编低质 vs 精编高质 |
| **海域适配** | 出战前已知海域环境修正(冻洋铁壁+) | 跨海作战必须换队 |

> 关键：这 5 维让「编队」本身是一个**组合优化谜题**，不是数值比大小。

## §3 情报与预测系统（为什么编队不是盲猜）

纯 auto 最易无聊的点：看不见敌人就组队 = 掷骰。**必须给玩家「读」的素材**：

1. **侦察情报**：开战前显示敌方舰队摘要——体系分布、威胁卡（高 atk/控）、预估战力。
   - 分级：完整情报(付费/探索解锁) / 模糊情报(仅体系) / 盲(历史事件)。构成信息差梯度。
2. **预测预览（UI 常驻）**：编队界面实时算并展示——
   - 对当前敌情：本队**克制 +X% / 被克 −Y%**
   - **combo 触发提示**：「火墙(烧+扛) 已满足」「锁定爆发(控+打) 已满足」
   - 这就是把我设计的「克制环 + combo」从纸面变成**玩家能看见的策略仪表盘**。
3. **复盘高亮**：战斗日志标「你被铁壁克 30%」「火墙触发」→ 玩家学到，下次改队。

> 设计意图：把「数值对撞」变成「玩家能看见、能预测、能学习的博弈」。

---

## §4 卡牌如何「被玩」（auto 下）

- 卡牌技能 = **被动触发**：满足条件自动发动（例：「开场若我方有铁壁，触发火墙」）。
- 玩家**不手动发动**，但在编队时**决定哪些触发条件被满足**——**组队即编程（programming by composition）**。
- 这把传统「出牌」的 fun 转移到「编队时设计触发链」：你不是在打牌，你是在**搭一台会自动打赢的机器**。
-  consequence：每张卡的 `synergy/countered_by/strong_against` 不是 wiki 知识，而是**编队界面的实时约束提示**。

## §5 战斗演出框架（纯演出，但必须有设计）

既然这是玩家战斗期间**唯一体验**，它就是产品本身。设计四块：

### 5.1 分镜结构
```
开场(双舰队入场, 镜头拉远) → 交战(逐段) → 高潮(combo特写/慢镜) → 结算(胜负+MVP+掉落)
```

### 5.2 可读性三原则（必须先于爽感）
1. **克制高亮**：被克方冒红光 / 减益图标，一眼看出「谁压谁」。
2. **伤害类型色**：烈焰橙 / 铁壁银 / 疾风青 / 潮汐紫 —— 颜色即信息。
3. **可暂停·可回放**：因无操作，给玩家「研究权」。时间轴拖动 = 学习工具。

### 5.3 爽感来源
- combo 触发专属演出（火墙=烧+盾同屏；锁定爆发=定身+集火）。
- **以弱胜强** underdog 特写（低战力翻盘时镜头推近）。
- **以彼之道**：被克方反手触发同队 combo 的「反制即协同」闪回。

### 5.4 节奏控制
- 快攻(疾风) 演出短促利落；鏖战(铁壁) 演出厚重拖拍——**体系性格由演出节奏外化**。

---

## §6 胜负与目标条件（给编队不同优化方向）

不止「HP=0 全灭」，多目标让编队有分化：
- **PVE 占岛**：击破守军核心(非全灭) / 存活 N 回合 / 零损(完美通关)。
- **PVP**：全灭 or 残余战力比排名。
- 同一队因目标不同(速通 vs 无损 vs 克制秀) 编法不同 → 再加一层策略。

## §7 这对「AI 出 demo」意味着什么

1. **后端**：`ResolveBattle(fleetA, fleetB, env, seed)` 保持纯函数、无 command 输入 → 确定性/zk 更干净（A 比 B 还好）。
2. **前端演出层是 demo 成败关键**：纯 auto 下玩家只看得见演出，所以 **demo 必须先把 §5 演出框架做成可跑原型**，否则「数值对撞」观感坐实。
3. **编队 UI = 第二关键**：§3 的预测仪表盘必须实现，否则「玩法」不可见、不可学。
4. **AI 分工**：战斗 agent 只写纯函数；演出 agent 吃 §5 规范做前端；编队 agent 吃 §2/§3 做 UI。常量只在 `constants.md`。

## §8 仍待你拍板的设计点
- 情报分级的具体信息差（盲战是否进 demo？）。
- 位序是「前中后排」还是「速度序」还是两者都有？
- 预设目标是「单选指令」还是「多指令优先级列表」？
- 演出是 2D 还是 3D 原型（影响 demo 成本）？
