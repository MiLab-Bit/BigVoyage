# ADR-003 · zk 战斗验证策略

- **状态**：Proposed（⚠ 阻塞于对齐假设 A-01 / A-02，需策划裁决后方可实施 P2）
- **日期**：2026-08-02
- **决策人**：程基岩（engineering-lead）
- **相关**：`battle-core-zk-readiness-audit.md`（预算依据）、`aleo-onchain-architecture.md`

---

## 1. 上下文

项目的链叙事核心是「**zk 可验证的确定性战斗**」。`ResolveBattle` 是纯函数，看起来是天然的 zk 入口。
但审计（`battle-core-zk-readiness-audit.md`）给出的预算结论是：

```
FLEET_SLOTS=5 · GUARD_MAX_ROUND=30 · MAX_EXTRA_HIT=2
→ 全场 _strike ≤ 900 次
→ 保守估算 ≈ 1.0M+ 约束（其中日志 Merkle 占 ~780k）
```

zk 电路必须完全展开循环、死分支也计入约束。**百万级约束的单一 transition，
在 Aleo 当前证明系统下不现实**（玩家客户端证明耗时/内存均超出可承受范围，浏览器 wasm 尤甚）。

同时代码有 5 项 zk 阻断（浮点、承诺不完备、RNG 未用、排序不稳、全局状态），
其中承诺不完备与排序不稳**在不上链的情况下也是 bug**。

矛盾：**比赛需要 zk 亮点，但全量战斗证明不可行。**

---

## 2. 备选方案

### 方案 A · 全链上重算

在 Leo 的 `async function` 里重跑完整 30 回合战斗。

- ❌ **根本性误解**：`async function` 是全网节点重算的公开执行，做重计算等于让每个节点跑 900 次 strike。fee 与出块时间均不可承受。
- ❌ 战斗输入（编队）会完全公开，丧失 record 隐私这一核心卖点。
- **否决。**

### 方案 B · 纯承诺（不做证明）

只把战报哈希上链，不做任何 zk 证明。

- ✅ 成本近零，立即可做
- ✅ 能防"事后篡改战报"
- ❌ 防不了"一开始就是假的"——凭空造牌、超 COST 编队全部无法阻止
- ❌ 作为**最终形态**，比赛叙事撑不住（评委必然追问）
- **作为 P0 阶段可，作为终局不可。**

### 方案 C · 递归/分段证明

把战斗切成 per-round segment proof，递归聚合后链上验根。

- ✅ 理论上可支撑全规格 30 回合
- ❌ 工程复杂度极高（递归电路、聚合器）
- ❌ **知识缺口 G-01**：Aleo/Varuna 上递归证明的成熟度我没有可靠数据
- ❌ 远超比赛周期可承受的工程量
- **超出当前能力半径，不选。**

### 方案 D · 乐观验证 + 挑战期欺诈证明

默认接受客户端提交的 `(commitment, winner)`，开挑战窗口；争议时才要求生成证明。

- ✅ 常态成本 ≈ 方案 B，极低
- ✅ 博弈上有效：只要挑战有利可图且任何人可挑战，作弊期望收益为负
- ❌ 占岛不是即时终局（有 N 区块"结算中"）
- ❌ 仍需一个"争议时能生成的证明"作为后盾——所以**不能单独存在**，必须搭配 E

### 方案 E · 降规格「链上裁决战」全证明

不把现有 30 回合战斗硬塞上链，而是**为链上单独设计一个规格天然适配电路预算的战斗模式**。

```
DUEL_SLOTS = 3, DUEL_MAX_ROUND = 8, MAX_EXTRA_HIT = 1
→ _strike ≤ 8 × 6 × 2 = 96 次
→ ≈ 66k 约束（约为全规格的 1/15）
→ 进入可证明区间
```

- ✅ 唯一能给出"完整战斗 zk 证明"的可行路径
- ✅ **玩法与技术的交集**：短平快的高强度决斗本身是好玩法，不是技术妥协的产物
- ✅ 保留全规格 30 回合战斗用于 PvE 主线（链下），两套规格各司其职
- ❌ **需要策划新增一个玩法模式**（A-01），不是纯工程决策
- ❌ 需要定点化先完成（A-02）

### 方案 F · 只证明输入合法性（不证明战斗过程）

用 record 所有权 + 电路断言证明「编队合法且卡牌归我」，不证明战斗过程。

```
断言：Σ COST_BY_RARITY[rarity] ≤ 10
      popcount(slot_mask) ≤ 5
      任一 system 计数 ≤ 4
      commitment == Poseidon8(...)
→ ≈ 3k 约束
```

- ✅ **性价比极高**：3k 约束封死链游最大的作弊面
- ✅ Aleo record 消费即证明所有权，几乎零额外成本——**这是 Aleo 的原生优势**
- ❌ 防不了"伪造自洽战报"

## 3. 决定

**不选单一方案，采用 B → F → D → E 的分层递进。**

| 层 | 阶段 | 方案 | 约束数 | 封死的作弊 |
|---|---|---|---|---|
| **L1 承诺** | P0 | B | ~0 | 事后篡改战报 |
| **L2 输入证明** | P1 | **F** | ~3k | **凭空造牌、超 COST 编队**（占实际作弊绝大多数） |
| **L2.5 乐观验证** | P1.5 | D | ~0 常态 | 伪造战报（经济上不划算） |
| **L3 全证明** | P2 | E | ~66k | 伪造战报（密码学上不可能） |

### 3.1 核心判断：优先级按「作弊门槛 ÷ 防御成本」排，不按严重度排

```
凭空造牌 / 超 COST 编队
    作弊门槛：极低（记事本改 JSON）
    防御成本：3k 约束
    → 必须最先做

伪造自洽 900 条战报
    作弊门槛：极高（需完整逆向定点规则引擎并保证全程自洽）
    防御成本：66k ~ 1M 约束
    → 可延后，先用挑战期的博弈成本替代
```

**这条判断是本 ADR 最重要的内容。** 常见的错误是一上来追求"完整战斗 zk 证明"这个最性感的目标，
结果耗尽预算，却连"改 JSON 白嫖 UR 卡"都没挡住。

### 3.2 立即执行（不依赖任何链上决策）

审计 P0 三项，可**立刻**在现有 Demo 分支修复：

| 项 | 内容 |
|---|---|
| BLK-2 | 承诺改为 `Poseidon8(ruleset_hash, fleet_a_h, fleet_b_h, env_h, seed, winner, rounds, log_root)`，**禁止截断** |
| BLK-4 | 排序键改为 `(spd DESC, side ASC, slot_index ASC)`，不依赖库的稳定性 |
| BLK-5 | 引入 `ruleset_hash` 显式入参，`GameData` 降级为默认值注入 |

这三项让 D3 验收从「单机一致」升级为「**跨端一致**」——而跨端一致是链上可验证的前提。

### 3.3 日志承诺用 Merkle 树，不用链式哈希

链式 running hash 可省 ~390k 约束，但**丧失局部开示能力**。
挑战期（方案 D）需要被挑战方只披露被质疑的几条日志（保住编队隐私），因此**接受 Merkle 的额外成本**。

### 3.4 `seed` 保持"不影响战斗结果"

审计 BLK-3 发现 `rng` 声明后从未使用。**建议保持现状**：
电路内无需实现可验证随机（zk 游戏电路里最贵、最易出漏洞的部分），
不可预测性改由 **`CrewCard` record 的天然私有性**提供（对手看不见你的编队）。
⚠ 需策划确认（A-04）。

## 4. 后果

### 正面

- 每一层都是**独立可交付**的，任一层停下都是完整故事。比赛排期风险可控。
- **比赛最小可交付 = P0 + P1**（承诺规范化 + 输入证明），P1.5/P2 是加分项。
- P0 三项修复不依赖任何链上决策，**今天就能开工**，且顺带修掉两个现存 bug。
- 方案 E 把技术约束转化为玩法设计，"链上裁决战"是技术与玩法的真交集，而非妥协。
- 绕开可验证随机数（3.4），大幅降低电路复杂度与安全风险——这是本项目相对其他 zk 链游的结构性优势。

### 负面 / 需承担

- **对外叙事必须如实分层**。P1 阶段成立的命题是「使用你不拥有的卡牌 / 违反编队规则 = 无法生成有效证明」，
  **不是**「伪造战斗 = 不可能」。后者要到 P1.5/P2。
  向评委诚实分层反而是加分项——宣称 P0 的哈希 mock 就等于反作弊，一问就穿。
- **方案 E 需要策划新增玩法模式**（A-01）。这是跨职能依赖，不是我单方面能决定的。
- **定点化会改变战斗数值**（A-02），已有平衡性数据可能需重跑。
- 挑战期带来"结算中"状态，需 UX 配合包装成航海叙事（消息随船传回），而非 loading 转圈。

### 阻塞项

| ID | 阻塞内容 | 阻塞什么 |
|---|---|---|
| **A-01** | 链上裁决战能否降规格（3v3 / 8 回合） | **P2 全部** |
| **A-02** | 定点化引入的数值偏差能否接受 | **P1 定点化 + P2 全部** |
| **G-01** | Aleo 单 transition 约束上限、wasm 证明耗时 —— **无可靠数据** | P2 规格能否落地 |
| **G-02** | 可验证随机源（POI 掉落 1/480、1/960） | P1 上链后的真实漏洞，当前**无防线** |

---

## 5. 知识诚实声明

本 ADR 中所有约束数（3k / 66k / 1.0M）均为**基于电路结构的量级估算**，
未经 `leo` toolchain 真机验证。Aleo snarkVM 的单 transition 约束硬上限、
wasm 环境下的实际证明耗时、递归证明成熟度，均超出我可靠掌握的范围。

**建议在 P1 启动前安排 1~2 天技术穿刺**，用降规格电路跑真机基准，回填 G-01/G-02/G-03/G-04。
在此之前，本 ADR 的阶段划分可用于**方向决策**，但**不得作为排期承诺依据**。

## 6. 复核触发条件

- A-01 / A-02 被策划推翻
- G-01 实测显示 66k 约束在目标客户端上仍不可接受 → 需进一步降规格或放弃 L3
- G-02 有了可用的 Aleo 随机源 → 可重新评估 3.4 的 seed 决策
- 比赛剩余时间不足以完成 P1 → 退守 P0 + 部分 F，并相应下调对外叙事
